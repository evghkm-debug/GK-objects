# Подключение общей базы объектов

Код готов к подключению, но в этой ветке ещё нет действующего облачного проекта. Сначала подключить Supabase, затем выполнить эти действия в конкретном проекте пользователя. Нельзя подставлять выдуманные адреса и ключи или использовать публичную общую базу.

1. Создать или выбрать отдельный проект для GK-objects. Выбор платного тарифа требует отдельного решения пользователя.
2. Применить `migrations/202609100001_gk_sync.sql` один раз. Миграция создаёт четыре таблицы, RPC сохранения, правила доступа и закрытый бакет `gk-photos`. Существующие таблицы и данные не удаляются.
3. В Auth отключить свободную регистрацию. Создать сотрудников через административный интерфейс Supabase (почта и первоначальный пароль); не хранить пароли в GitHub. Письма от имени пользователя без отдельной просьбы не отправлять.
4. Создать строку `gk_workspaces` с названием команды. Для каждого созданного пользователя добавить `gk_members`: ID команды, ID пользователя Auth, отображаемое имя. Учётная запись без этой строки доступа к данным не получит. Управление составом команды доступно только администратору облачного проекта.
5. В `cloud-config.js` указать URL проекта `https://<project>.supabase.co`, **publishable/anon** ключ и UUID команды. Это публичные настройки. **service_role, sb_secret и пароли никогда не должны попадать в приложение или репозиторий.**
6. Проверить SQL-тесты и доступ двух отдельных тестовых пользователей через реальный API: вход, добавление/загрузка объекта, загрузка/чтение фото, запрет другой команде и анонимному посетителю. Ветки разработки и тестовые объекты не смешивать с живой базой.
7. Сохранить резервные копии с телефонов и опубликовать обновление на существующем GitHub Pages. При изменении публичного cloud-config увеличить версию кэша service worker и URL статических ресурсов.
8. На каждом телефоне войти. Для прежних локальных объектов нажать «Перенести … объектов в общую базу». Перед переносом локальная база не очищается. Если одинаковый ID имеет разные версии, локальный вариант сохраняется отдельной карточкой с отметкой для сверки.
9. Сверить количество объектов, контактов, площадей и фото на обоих телефонах. Протестировать отсутствие связи, восстановление связи и одновременное редактирование. До этой проверки не заявлять о готовности живой синхронизации.

## Устройство синхронизации

`objectsSurveyDB` остаётся локальным хранилищем доступных записей и очереди. Служебный `_sync` содержит версию, поколение локальной записи, признак изменений и идентификатор операции. Подтверждение сервера не очищает более новые локальные изменения. Передача происходит при сохранении с задержкой 1,5 секунды, возвращении в приложение, восстановлении связи, вручную или каждые 30 секунд, пока приложение открыто.

В PostgreSQL хранятся карточки и версии; фото находятся в закрытом Supabase Storage. Бинарные снимки заменяются в серверной карточке ссылками на SHA-256. Доступ проверяется по членству в команде. Прямые изменения таблиц из браузера запрещены; RPC проверяет исходную версию под блокировкой, сохраняет историю и поддерживает повторные запросы. Фото неизменяемые: перезапись и удаление из браузера не разрешены.

При конфликте серверная версия становится основной, а локальная сохраняется с новым ID и отметкой `reviewRequired`. Это сознательное сохранение двух вариантов для сверки, а не автоматическое объединение полей.

Выход скрывает общие записи в интерфейсе, но не удаляет локальные копии: это не шифрование диска телефона. Отозванный серверный доступ не может дистанционно уничтожить офлайн-копию.

## Ограничения текущего этапа

- Тесты базы выполнялись в изолированном PostgreSQL PGlite с имитацией системных схем Supabase; требуется проверка на действующем проекте после подключения.
- Кнопки фото проверены программно. Нативное меню, камера и попадание в галерею требуют проверки на смартфоне.
- Новые фото сохраняются с прежним сжатием; хранение оригиналов не добавлялось.
- Восстановление поддерживает прежний рабочий формат `survey.photos`. Несовместимая восстановленная v0.3.1 отклоняется до записи.
